# Approach: Screenshot-derived

- Source-of-truth priority: runtime code first, then screenshots/live previews, then docs. Screenshots inform, code decides; record divergences explicitly.
- Inventory every reference viewport first. Map each screen to a route or reusable pattern and identify what repeats across the set before choosing defaults. The repeated evidence decides whether the system is dark-first or light-first; never substitute generic convention for that evidence.
- Extract in order: layout skeleton → spacing rhythm → surface/elevation hierarchy → color roles (bg/surface/accent/text/status) → type scale → component inventory → responsive deltas.
- Tokenize with the repo's own prefix convention (`<prefix>-` + role, e.g. `--myapp-bg-primary`); semantic names, never raw hex above the token layer.
- Rebuild the screenshot's structure from system primitives; pixel-tweaking raw CSS to "look right" is forbidden — if no token fits, add the token.
- Be very accurate to the chosen source; never guess values a screenshot cannot resolve (mark TBD, check code). Interpolate only through reusable semantic tokens and document the source screenshot for every route pattern.
- References are design evidence — never invent product requirements, never copy sample data as real data, and never treat supplied art as licensed runtime media. When implementation was requested, the rebuilt UI still owes the complete system (`reference/master-instructions.md` §57), not just matching pixels.
- Create a required-element inventory for each target route before building. The inventory is a lower bound, not inspiration: every visible reference module must be rendered or have a documented product-specific replacement approved by the user.
- Keep routes isolated. Never use the public-home hero or footer as a substitute for an authenticated dashboard, market overview, wallet, spot, or futures workspace.
- A visual acceptance render must contain resolved representative content. Loading skeletons, empty/error states, blank panels, generic hero illustrations, and missing modules are only valid in their own state tests—not as the screenshot-comparison render.
- Add a side-by-side fidelity gate for each migrated route: source viewport structure/density, required-element inventory, semantic colour roles, type hierarchy, states, responsive collapse, and the authored alternate theme. A blank, loading, or fallback route is a blocker, never a pass.
- Screenshots define visual contracts, never the entire product inventory. Before any migration, enumerate the runtime route tree, layouts, navigation destinations, dialogs/drawers, API clients, helper-driven interactions, and relevant route states. Every current surface needs either a paired reference or a recorded closest-pattern decision; no screenshot is permission to omit a function.
- Behaviour proof is separate from visual proof. Record baseline controls, validations, real data dependencies, mutations, permission checks, and recovery paths before replacement; confirm them after. An authentic-looking static fixture, skeleton, or empty state cannot satisfy this gate.
- When an evidence-backed visual element has no safe current integration, isolate it from live data, label it honestly, and require a target-local missing-capabilities log with the proposed API/data contract, security/permission concerns, acceptance criteria, and removal condition. Never simulate a live order, balance, payment, identity, or reward.
